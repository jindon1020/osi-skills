# 结构化交互确认规范

把用户确认当作翻译设计输入。优先使用执行环境提供的结构化提问工具；没有时用简短、编号清晰的问题并等待回答。

## 原则

- 一次只问 1 到 3 个会真实改变实现的问题。
- 先给出基于源码和原 Skill 的推荐方案，再列 2 到 3 个互斥选择及影响。
- 不询问能从源码、节点目录或原 Skill 查证的事实。
- 用户已明确决定的事项不重复询问。
- 把答案、日期和产物变化写入 `design-decisions.md`。
- 用户否决候选图后先更新节点图、迁移表和 Skill 拆分，再继续实现。

## Checkpoint 1：节点与小 Skill 拆分

完成行为清单后展示：

```text
节点ID | 类型 | 业务职责 | 输入来源 | 输出 | Prompt/Skill/工具 | 副作用 | 原Skill来源
```

同时展示控制边、selector 数据依赖和小 Skill 表：

```text
小Skill | 承载Agent节点 | 多步骤职责 | 允许工具 | 来源内容 | Runtime可用性
```

只询问会改变设计的问题：

1. 哪些多步骤方法应拆成小 Skill 并放入 `agent@1`，哪些其实是明确的一次调用，应改为 `llm@1`？
2. 哪些稳定阶段应成为 `workflow@1` 子工作流，哪些保留主图节点？
3. 串行、foreach、loop 和停止路径是否符合业务预期？

推荐默认：一次推理用 LLM；可复用多步骤方法拆成最小小 Skill 并绑定 Agent；稳定且可独立回归的阶段用子工作流。

## Checkpoint 2：合同、JSON、能力与副作用

实现前展示并确认：

1. 公开输入 key 的英文映射。任何中文 key 都必须映射为 ASCII `snake_case`；若会影响调用方，明确适配责任。
2. 所有 AI JSON 输出的三次循环：`max_iterations=3`、每节点 `attempts=1`、第三次失败合同和校验规则。
3. 原脚本中的外部调用对应哪个已注册工具/节点。若没有，列为 Runtime 能力缺口并停止该部分，不回退到 `code@2`。
4. 哪些工具调用付费、不可逆或可能重复提交；平台 attempts 与业务 retry 如何分工。
5. 哪些分支需要 `human@1` 审批，action id 和继续/停止语义是什么。

若用户已经在任务中明确规定“JSON 最多三次”“输入 key 不用中文”“code 只做胶水”等，不重复提问，直接写入设计决策。

## Checkpoint 3：实现与发布

定向测试和确定性构建后展示：

- 最终节点、控制边、selector、端口 Schema 与确认方案的差异；
- Workflow `id/version/spec`、Package SHA256 和成员数；
- 小 Skill 名称、版本/来源、允许列表和目标 ResourceBinding 可用性；
- JSON guard 的实际 mock 调用次数与三次失败结果；
- Runtime 能力缺口及 code 节点静态审计结果；
- 真实外部链路、部署和冻结恢复的未验证项。

只有存在多个合理选择或需要新增授权时才提问，例如：

1. 仅保留候选包，还是在目标 Runtime 中认证？
2. 缺失的外部能力是否授权在 AgentOS 中另行开发工具/节点？
3. 是否提交、推送、上传、切 current、创建真实 Run 或部署；目标是什么？用户在当前任务里已经逐项授权的动作不重复询问。

设计确认不等于提交、发布或部署授权。

## 示例

```text
问题：Producer 阶段应如何承载？
推荐：拆出 producer-planning 与 producer-review 两个小 Skill，由一个 agent@1 绑定；内部需要按规则读取素材、调用工具并多步判断，属于稳定的自主方法。
选项：
1. 两个小 Skill + agent@1（推荐）— 责任清楚，可单独版本化。
2. 一个小 Skill + agent@1 — 文件更少，但规划和审核耦合。
3. 多个 llm@1 — 仅在每一步都是明确的一次推理、无需自主工具选择时适用。
```
